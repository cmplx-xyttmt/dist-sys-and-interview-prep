01What is a Sprite?

A Sprite is a full Linux VM (root access, real filesystem) that creates in ~1–2 seconds, keeps its disk forever, and falls asleep when idle — billing you almost nothing while it sleeps. You can scatter thousands of them without thinking about it.

"Ball-point disposable computers." Like cheap pens you stash in every drawer — you don't ration them, you don't name them, you grab one when you need it and forget it.
"A semi-disposable cow" (not a pet). It materializes exactly when needed and terminates when idle. The CEO's framing: they're computers for agents, not sandboxes for humans.

The tension that makes them interesting: a normal cloud VM forces you to pre-allocate, name, and pay for it whether or not it's working. A serverless function is cheap-when-idle but dies fast and forgets everything. A Sprite is the third thing — instant and disposable like serverless, yet a persistent stateful computer like a VM. Getting all three at once is the whole engineering story below.

02Why now — the agent framing

Sprites exist because Fly.io made a "specific and probably polarizing bet": that agent-driven development is about to dominate, and agents want different infrastructure than humans do.

Kurt Mackey's core claim: the "opinionated defaults" we built to make clouds convenient for humans actively get in an agent's way. An agent doesn't want a curated PaaS experience — it wants an explicit, stateful, disposable computer it can drive directly, break, checkpoint, fork, and throw away. Give an agent a bare Linux box with root and a durable disk, and it's happy.

🎯 Your direct hook: the lead-id agent harness

This is exactly the problem an agent harness solves, from the platform side. Each agent run wants: an isolated environment, a durable working directory it can accumulate state in, the ability to pause/resume across a long task, and credentialed access to external systems without handing the agent your secrets. Sprites ship all four as primitives (durable fs, checkpoint/restore, Connectors). Reading how Fly built this is a blueprint for the harness you're building at work — and a source of real design questions to bring back.

03The three design bets

Sprites run on Fly Machines (Firecracker microVMs) but make three inverted assumptions. Each one trades a convention away to buy instant + durable + disposable. Click to dig into the reasoning.

1 Kill the container image ›

"Most of what's slow about creating a Fly Machine is containers" — pulling and unpacking an OCI image is the 60-second tax. Sprites skip it entirely: every worker already has a standard pre-positioned container, and Fly keeps pre-warmed pools of "empty" Sprites ready. Creating one becomes just the fast startup step that was already optimized.

The lesson: the fastest work is work you did ahead of time. Pre-warming + a shared base image turns "provision" into "claim." This is the same move behind connection pools, JIT-warmed lambdas, and object pools.
2 Object storage is the source of truth ›

Instead of anchoring a Sprite to the NVMe of one physical server, its durable state lives in S3-compatible object storage. Consequence: "the durable state of a Sprite is simply a URL." No server binding, so migration is trivial and a dead physical doesn't mean a lost (or slowly-restored) Sprite — you just re-open the URL somewhere else.

The lesson: separate durability (object storage, boringly reliable) from performance (local NVMe cache). Make the source of truth cheap, replicated, and location-independent; treat local disk as a disposable cache. This is the cloud-native storage pattern — see the storage-stack section.
3 Inside-out orchestration ›

Most platform logic runs inside the VM, not on the host. Your code runs in an inner container; the VM's root namespace hosts the platform services — the storage stack, a service manager (restarts), logging, and network binding/proxy integration. The host stays dumb.

The lesson: pushing logic into the guest shrinks the host blast radius (a bug isolates to one VM, not the fleet) and lets them ship platform changes without touching every physical. Ptacek: these decisions "make Sprites drastically easier for us to scale and manage."

04The storage stack — how a disk becomes a URL

This is the technical heart, and it's a distributed-systems master class — you already have most of the vocabulary from DDIA. Click each layer.

🔥 NVMe cache performance
Local disk, read-through — like dm-cache. Fast reads without being the source of truth.
Because the underlying data chunks are immutable, "nothing in that NVMe volume should matter" — you can lose it and re-fetch. That immutability is what kills the hardest problem in caching: invalidation. A chunk never changes, so a cached chunk is never stale.
🗂️ Metadata: SQLite + Litestream the index
Which chunks make up the filesystem, and where. A local SQLite DB, made durable by streaming its writes to object storage.
Litestream continuously ships SQLite's write-ahead log (WAL) to object storage. So the metadata gets the same "truth lives in S3" treatment as the data. This is log-shipping replication — the exact idea from DDIA's replication chapter, applied to a single-file database.
📦 Data chunks: object storage (S3) durability
The filesystem's actual bytes, split into immutable chunks and stored in S3. Boringly, massively reliable.
This is the JuiceFS model: split files into content chunks, store chunks in object storage, keep a separate metadata index that maps files → chunks. Separating data from metadata is a pattern you'll recognize from GFS/HDFS. It's what lets the durable state be "just a URL."

Put together: data (immutable chunks in S3) + metadata (SQLite, WAL-shipped to S3) + a throwaway NVMe cache in front. Durability comes from object storage; speed comes from the cache; and because chunks never mutate, the two never fight.

05Checkpoint & restore — cheap enough to use casually

Sprites make checkpoint/restore a first-class, everyday operation, not an emergency escape hatch.

🤔 Predict first: why can a Sprite checkpoint be so fast that Fly wants you to use it "like a git restore, not a system restore"?
Because both checkpoint and restore merely shuffle metadata around. The data chunks are already immutable and already in object storage — a checkpoint doesn't copy gigabytes, it records which chunks + which metadata snapshot constitute this point in time. Restore reconstructs from that. It's the same reason a git commit is fast: content is content-addressed and shared; you're only writing a new pointer over an immutable object graph.

Drive forking extends this: clone a template Sprite cheaply via a copy-on-write Sprite Block Device (SBD) — spin up 100 agents from one warmed template without copying its disk 100 times. And Connectors give a Sprite authenticated access to external systems without exposing the credentials to the code running inside — the "give the agent capability, not secrets" pattern.

Networking aside: public URLs propagate via Corrosion, Fly's gossip-based service-discovery layer — "a Corrosion update that propagates across our fleet instantly." Keep that word gossip in mind; it's a direct bridge to your Glomers track.

Honest limits (Fly says so themselves): object storage is too slow to be "a hot Postgres node in production"; production CI/CD expects OCI containers; warm e-commerce workloads don't like aggressive sleep. The intended arc is prototype on Sprites → containerize for production Machines. Knowing where a tool stops working is exactly the judgment a senior interview probes for.

08Small projects to get a hang of them

Ordered easy → hard. Each isolates one Sprite primitive so you build the intuition from the ground up — in Python where it's for learning, Go where it doubles as Glomers.

Level 1 · feelDrive a Sprite (or a Fly Machine) by hand
Build: spin one up, put files on the disk, checkpoint, kill it, restore, confirm the files survived. Fork a template into 3 and run a trivial agent in each.
Teaches: the create→checkpoint→restore→fork loop as muscle memory. No theory yet — just the feel of "computers as pens."
Level 2 · storageToy content-addressed chunk store
Build (Python): split a file into fixed-size chunks, hash each, store chunks by hash in a dir (or MinIO/S3), keep a JSON manifest mapping file → ordered chunk hashes. Reconstruct the file from the manifest. Add a second file that shares chunks — watch dedup happen for free.
Teaches: the JuiceFS core — data/metadata separation, immutability, content-addressing, why "the disk is a URL" is possible.
Level 2 · replicationWAL-ship a SQLite DB
Build: run Litestream against a SQLite DB replicating to MinIO; kill the DB, restore from object storage, verify. Stretch: hand-roll a tiny WAL tailer that ships frames yourself so you see the mechanism, not just the tool.
Teaches: log-shipping replication + point-in-time restore — DDIA Ch. 5 made tangible. This is the Sprite metadata layer.
Level 3 · gossipBroadcast → then read Corrosion
Build (Go): Gossip Glomers challenge 3a–3e — a gossip broadcast system over Maelstrom (already on your plan). Then read how Corrosion propagates fleet state and map your toy onto their real one.
Teaches: gossip dissemination, fanout vs latency, partition tolerance — and it's already a checkbox on your roadmap. Double-counts.
Level 4 · capstoneDesign (don't build) a mini agent-sandbox platform
Write: a system-design doc for "durable sandbox-per-agent-run" for lead-id — durable working dir, checkpoint on pause, fork from a warm template, credential brokering. Use your 4-step skeleton. Compare your design to how Sprites actually did it.
Teaches: synthesis. Turns everything above into an AI-era system-design answer that plays to your unfair advantage — and feeds directly into real work.
