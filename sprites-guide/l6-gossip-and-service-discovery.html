1 · After this rung you can say

  • how a gossip protocol spreads a fact: each node tells a few random peers each round, so the whole fleet knows in a number of rounds proportional to the logarithm of its size
  • what SWIM (Scalable Weakly-consistent Infection-style process group Membership, the 2002 protocol behind Serf and Consul) does: nodes ping each other and gossip about who is alive
  • what a CRDT (conflict-free replicated data type) is: a data structure whose replicas can be updated independently and always merge to the same result, without a coordinator
  • what service discovery means (finding which machine currently serves a name), and how a Sprite's public URL finds the physical host it lives on right now: Fly's Corrosion gossips that mapping across the fleet

3 · Mission model it (already on the dist-sys roadmap as a Gossip Glomers challenge)

Do this
  1. Install Maelstrom, the test harness Fly's Gossip Glomers challenges run on. It starts your program as several nodes, sends them requests (a workload), can cut the network between nodes (a partition, injected by what it calls a nemesis), and checks the results. brew install openjdk graphviz gnuplot, download the latest release tarball from github.com/jepsen-io/maelstrom/releases, unpack it.
  2. Fly's pages show Go; you are writing Python. Your node is a script with a #!/usr/bin/env python3 first line and chmod +x, reading one JSON message per line from stdin and writing one per line to stdout (about 40 lines of scaffolding from the protocol reading). Pass challenge 1, Echo: ./maelstrom test -w echo --bin ./echo.py --node-count 1 --time-limit 10. "Everything looks good!" means valid.
  3. Challenge 3a, single-node broadcast: --node-count 1. Challenge 3b, five nodes, every node must end up with every message: forward each new message to your neighbours. ./maelstrom test -w broadcast --bin ./broadcast.py --node-count 5 --time-limit 20 --rate 10.
  4. Stretch, the second week: 3c, the same under partitions, --nemesis partition. Messages sent during a partition must be retried until acknowledged, and a node must be able to receive a message twice without double-counting (that property is called idempotence). Then read the Corrosion README and write ten lines mapping your broadcast onto it: what is gossiped, how conflicts resolve (Corrosion uses CRDTs over SQLite), what happens during a partition.

The check: Maelstrom prints "Everything looks good!" for echo, 3a and 3b. For 3c (stretch) the same, and from its results block record :msgs-per-op under :net :servers, the number Glomers 3d later asks you to lower. The ten-line mapping exists.

Hint · If 3c fails under partition

Two bugs cover most failures: you send once and never retry, or you retry and count duplicates. Keep a set of seen message ids, and keep a per-neighbour queue of unacknowledged messages that you resend on a timer.
