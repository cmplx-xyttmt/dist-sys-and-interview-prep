Terms used below

  • graph-player and the content-graph format: the small interactive course player prototyped in curriculum-edtech/content-graph.html and planned in mvp-plan.md; a course is a JSON graph of nodes (sections) with prerequisite edges.
  • Mission and the transfer test: a short task with a runnable check, from learning-through-code-and-maths.md; the transfer test asks whether a strong programmer who never read the source could pass it (they must not).
  • Few-shot examples: worked examples placed in the prompt so the model imitates their shape.
  • Readability extraction: pulling the article text out of a web page, dropping navigation and ads (the Readability algorithm, as in Firefox's reader view).
  • Supadata: the transcript service already connected in Isaac's tools, used for YouTube transcripts.
  • sprites-py: Fly's Python SDK for the Sprites API.
  • ulimit and a network namespace: Linux limits on a process's CPU, memory and file use, and an isolated network view with no outbound access; both are how the check runner is kept from wedging the Sprite.
  • Onirele: the Ugandan exam-question contact; MVP: the edtech minimum viable product from mvp-plan.md; P0 to P4: the five build phases in the table below.

The one-liner

Paste a link to something you want to learn (an article, a docs page, a paper, a video with a transcript). The platform builds you a course: an outline, section summaries at your level, quizzes with explanations, and checkpoints, which are short missions with a runnable check. It tracks what you've passed and schedules review. A browser extension adds a "Learn this" button so you never leave the page.

Every learner gets their own computer for it: a Sprite.

Why Sprites, and the one claim the design rests on

A plain web app (Postgres, a worker queue, an LLM call) can generate a course from a link. So the design has to earn each Sprite primitive it uses, or it's a demo of Sprites wearing an edtech costume. Here is what each buys, and where it's honest to say a database would do.

The load-bearing claim: the Sprite earns its place because the learner runs code. Checkpoint missions (from learning-through-code-and-maths.md) are small programs with a check, generated for the source, and the learner's attempts execute in their own VM. Take that away and the honest design is a web app. So the missions are not a feature; they are the reason for the architecture.

Architecture

Three parts, small on purpose.

The librarian (control plane). One small service (FastAPI or Django, the Django app is what Tunga uses). Owns accounts, maps each learner to a Sprite id, accepts "learn this URL" jobs, and talks to the Sprites REST API (api.sprites.dev/v1/sprites/, or the sprites-py SDK). It can itself run on a Sprite. It never holds course content.

The study computer (one Sprite per learner). Runs course-agent, a Python program with five stages, a checkpoint between each:

  1. Fetch. Readability extraction for articles, PDF text for papers, the Supadata transcript connector for videos. Saves source/ and a normalized source.md.
  2. Plan. LLM call through the OpenRouter connector: outline as JSON in the content-graph format already prototyped in content-graph.html (nodes, prerequisites, edges). The learner's stated level goes in the prompt.
  3. Generate. Per node: a summary at level, three quiz questions with explanations for each wrong option, and one checkpoint mission: a small world (fixture), a source-dependent unknown, a runnable check (check.py or check.js), written against the mission template. The transfer test is a prompt-side rule: the check must fail for a strong programmer who hasn't read the source.
  4. Serve. A static site plus a tiny API on port 8080: the course, the quizzes, a "run check" endpoint that executes the learner's attempt inside the Sprite and returns pass or fail with the check's output. This is the graph-player from mvp-plan.md, now with a check field.
  5. Track. progress.json, a review queue (spaced), and a "regenerate this node" action that restores the pre-generate checkpoint for that node and reruns stage 3 for it only.

The button (browser extension). Thirty lines: reads the tab URL, POSTs it to the librarian with the learner's token, opens the course URL when the Sprite reports ready. Also a paste box on the site for people who won't install extensions.

Data flow for one "Learn this": extension posts URL to librarian; librarian finds or creates the learner's Sprite (create, bootstrap, first checkpoint), then execs course-agent learn <url> inside it; the agent runs the five stages with a checkpoint after each; the librarian polls the Sprite's status endpoint and returns the course URL. The Sprite then sleeps until the learner opens the link.

Risks, in order of how much I'd worry

  1. Three framings in 24 hours. MVP slice with Onirele, the missions generator, and this. They're one product from three sides (content, pedagogy, infrastructure), but three framings in a week is how eight months of unfinished projects happened. Sep 24 picks one "done" sentence and the other two become sections of that plan, not alternatives.
  2. Generation quality. Quizzes come out shallow and missions come out as coding exercises unless the prompts enforce the transfer test and a human reads the first twenty. Budget a review pass in P0; keep the twenty best as few-shot examples.
  3. Cost per course. Fetch plus plan plus per-node generation is maybe 50k to 150k tokens for a long article. Fine for you; a pricing question before anyone else uses it.
  4. Sprites limits. Plan tiers cap concurrent Sprites; fork is not native; the S3 block device is early access. P1 needs one Sprite, P2 needs two. Check the allowance before Oct 1.
  5. Untrusted code inside the learner's own VM is safe for the platform (it's their machine) but the check runner still needs a timeout, a memory cap and no outbound network, or a mission can wedge the Sprite. ulimit and a network namespace for the runner in P3.
