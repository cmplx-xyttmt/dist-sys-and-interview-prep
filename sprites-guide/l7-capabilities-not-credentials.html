Capabilities, not credentials

One rung per week: the reading in the Thursday 19:30 system-design slot, the mission the following Tuesday 19:30. Tick as you go; the checkpoint at the bottom is what marks the rung passed.

1 · After this rung you can say

  • the difference between holding a credential (the API key itself) and holding a capability (an unforgeable right to perform one action, which can be handed out and revoked)
  • what a token broker is: a process that holds the real secret and performs calls on behalf of a less-trusted process, adding the secret itself. The secret usually travels as an HTTP header, Authorization: Bearer <key>
  • why an agent's machine should never contain the raw key: anything with root on that machine (including the agent's own mistakes) can read it
  • how Sprites Connectors implement this: the Sprite reaches OpenRouter (a service that fronts many language-model APIs behind one key), Slack, GitHub or any HTTP API, and the credential never enters the VM. OAuth is the web's standard way for one service to grant another limited access on a user's behalf; Connectors hide its dance too

3 · Mission model it (new; not in the explainer)

Do this

The check: The agent gets 200 through the broker. Every leak attempt fails: the key is not in the agent's environment, not in any file it can read, and /proc/<broker pid>/environ is permission denied (it belongs to root). Record the status code, the number of attempts, and the number that succeeded, which must be zero.

Hint · If the agent can read the key

Both processes run as the same user, so /proc/<pid>/environ is readable. Check ps -o user,pid,cmd. Running the agent as a different user is the whole mechanism; the VM boundary in Sprites is a stronger version of the same line.
