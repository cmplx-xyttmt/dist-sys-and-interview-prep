Rung 0 of 8 · operating systems · about 2 h (reading 1 h, mission 1 h)

A computer from the inside

One rung per week, in two sessions: the first half on Thursday at 19:30, the second half the following Tuesday at 19:30. Tick as you go; the checkpoint at the bottom is what marks the rung passed.

1 · After this rung you can say

  • what a process is, and what the kernel does that a process can't (talk to hardware, hand out memory, decide who runs)
  • what a filesystem is (names, directories, an index of which blocks hold which file) versus the block device under it (a disk seen as a numbered array of fixed-size blocks, typically 4 KB). Step 1's reading, below, covers this
  • why a container is a normal process with a restricted view of the machine (the kernel features are called namespaces and cgroups; step 6's reading, below, defines them) and a virtual machine is a whole second kernel with its own emulated hardware
  • what a container image is: a stack of tar archives plus a JSON manifest, in the format the Open Container Initiative (OCI) standardised; and why pulling and unpacking one is the slow part of starting a container
  • what a microVM is: a virtual machine with almost no emulated hardware, so it boots in milliseconds. Firecracker is the one Fly uses under every Sprite

2 · Work through it, in order

Read a little, then do a little. The ticks and the boxes save in this browser, with the rest of the ladder.

First half · Thursday, about 84 minutes

  1. Everything in this rung happens in one folder, with one terminal window. Docker Desktop takes a minute or two to start and you won't need it until step 5, so start it first. The step numbers here match the names check.py uses. Copy and paste this:

    cd ~/Projects/dist-sys-interview-prep/sprites-guide/rungs/l0 && open -a Docker && python3 check.py

    What you should see: five lines. setup says PASS once Docker is up ("not running yet" is fine for now; run it again in a minute), and step2, step4, step5 and step7 say TODO. Each do-step has a starter file in that folder with TODO lines where your code goes. Nothing to install.

  2. Start with the first two bullets of "After this rung you can say" above: a process and the kernel, and the filesystem versus the block device under it. Two minutes.

    Then open OSTEP, "File System Implementation". Read from the start through the section titled "Overall Organization", and stop when the next section (about the inode) begins. That's about two pages. Look hard at the picture of the 64-block disk; you'll use its numbers in step 4.

    Before you read, guess here: how does the filesystem get from the name notes.txt to the disk blocks holding its bytes? What is stored about a file besides its bytes?

  3. The chapter says the disk is split into 4 KB blocks. Is your Mac's disk like that? Ask it:

    diskutil info / | grep "Block Size"

    Now open step2_blocks.py and write the two functions marked TODO: blocks_needed (how many 4 KB blocks a file of some size needs) and allocated_bytes (how much disk the filesystem says a file takes, from os.stat). The docstring for allocated_bytes has a warning about units. Read it. Then:

    python3 step2_blocks.py
python3 check.py step2

    What you should see: step2: PASS and a small table. A 1-byte file takes 4096 bytes on disk, and a 4097-byte file takes 8192. If the check says you are off by a factor of 8, that is the units warning.

  4. Back to the OSTEP chapter. Read the section titled "File Organization: The Inode", up to where it starts on multi-level indexes. The part to slow down on is the worked example that finds inode number 32. Say each step of that arithmetic out loud once.

    Alongside, try it on a real file. The first number ls -i prints is the inode number:

    ls -i step2_blocks.py
stat step2_blocks.py

  5. Open step4_inode.py. The constants at the top are the chapter's example filesystem: 4 KB blocks, 256-byte inodes, an inode table starting at 12 KB. Check them against the picture first. Then write the three functions: the byte address where an inode starts, the block that holds it, and the sector that holds its first byte. The chapter's own example (inode 32 starts at 20 KB) is your first test.

    python3 step4_inode.py
python3 check.py step4

    What you should see: step4: PASS. The check's last line says something about inodes 0 to 15. The disk only reads whole blocks, so what does looking up one file's inode fetch for free?

  6. A container image is a stack of archives that has to be downloaded and unpacked before anything can run. Starting a container from an image you already have is a different cost. How different?

    Guess before you measure. Open step5_timing.py and fill in the two predictions in seconds: the pull of python:3.12 from nothing, and one docker run once it's local. Then start the measurement (it removes any local copy first, so the pull is from nothing):

    python3 run_timing.py

    What you should see: Docker's download progress, then pull: ... s and three run times. The image is around 1 GB, so the pull can take a few minutes. Don't wait for it. Go to the next step and come back when it prints "Saved timings.json". Then write median() in the same file and run python3 check.py step5. PASS if your ratio was within 3x; if not, the check asks for one sentence in SURPRISE on what you had wrong. That sentence is the most useful thing you'll write tonight.

  7. While the pull runs, read Julia Evans, "What even is a container: namespaces and cgroups". Note the word namespace each time it comes up, and what it hides.

    Before you read, guess here: is a container a process, a virtual machine, or a third thing? Three containers are running on one machine: how many kernels are running?

  8. On a Mac there's a twist. The machine a container runs on is not macOS. Docker Desktop runs a hidden Linux virtual machine, and every container is a process inside it. So "outside" means that VM, and run_compare.py reaches it with nsenter.

    Open step7_inside_outside.py. For each of five commands, predict whether the container prints the "same" output as the Linux VM or "different" output. Then one True or False: when a container runs sleep 300, can the VM's process list see it? Fill everything in, then:

    python3 run_compare.py
python3 check.py step7

    What you should see: the five commands in three places (your Mac, the VM, the container), then the check marks each wrong prediction. For each one, write a sentence in NOTES and run the check again until it says PASS. Look at the kernel version line in particular.

First half ends hereRun python3 check.py once more. Five PASS lines means the first half is done. If you run out of energy after the container-pull step, stop there instead: the last two steps open Tuesday, and that's fine. A short evening that ends with a passing check beats a long one that doesn't.

Second half · the following Tuesday, about 55 minutes

  1. Read sections 1 and 2 (about three pages) of Firecracker: lightweight virtualization for serverless applications (NSDI 2020).

    Before you read, guess here: why wasn't a container good enough for AWS Lambda? Why wasn't an ordinary VM? What boot time does the paper aim for, and what did it remove to get there?

  2. Open compare.json from the first half: it is your evidence. Write five lines in the box: what the container shares with the kernel it runs on (the process list you could see from outside, the kernel version), and what it has its own copy of (hostname, mounts, the process tree it can see). Use Firecracker's framing where it helps: which of these would a microVM have its own copy of too?

  3. Skim the OCI image specification overview (optional reading, 10 minutes): layers, manifest, config. Then open the image you pulled in the first half and look at the layers that made the pull slow:

    docker save python:3.12 -o /tmp/img.tar && tar tf /tmp/img.tar | head -20
rm /tmp/img.tar

    Before you look, guess here: how many files is a container image? What is in the manifest?

Second half ends hereThen pass the rung with the checkpoint below: your two timings, your predicted ratio, and the five lines.
Hint · If the pull is fast anyway

You are on a fast connection and the image is small. Pull something bigger, such as pytorch/pytorch (several GB), or read the pull's output: it lists the layers, and each is one of the tar archives from the say-list. The 60-second tax the explainer's first design bet removes is real on Fly's side because their images are bigger and their network path longer.
