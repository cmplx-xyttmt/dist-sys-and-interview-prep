## After this rung he can say

- the three places a written byte can be before it is safe: your program's own buffer (Python's file object), the kernel's page cache, and the disk. Which crash loses which: a killed process loses only its own buffer; a power cut or kernel crash loses the page cache too; only fsync (the system call that forces the page cache to disk) protects against the last one
- what SQLite is: one file, organised as fixed-size pages arranged in a B-tree (a sorted, shallow tree of pages), read and written by a library inside your process rather than a separate server
- what a write-ahead log (WAL) is: every change is appended to a log and made durable before the main structure is updated, so a crash mid-update loses nothing that was acknowledged
- why "append to a log, then apply" is the move underneath every durable system in the explainer: SQLite's WAL, Litestream, and the storage stack's metadata layer

## The steps

### Step 0 · read · Reading 1: Ben Johnson, SQLite internals: pages and B-trees

Read Ben Johnson, SQLite internals: pages and B-trees (https://fly.io/blog/sqlite-internals-btree/), core. 15 min. What a page is, how the B-tree sits on pages.

Alongside: `sqlite3 t.db 'create table x(a); insert into x select value from generate_series(1,1000000); pragma page_size; pragma page_count;'`. Compare the page count with the post's arithmetic.

Guess questions (ask before the reading or the prediction):
- What is SQLite's page size? How many tree levels does a table of a million rows need?

### Step 1 · read · Reading 2: Ben Johnson, SQLite internals: WAL

Read Ben Johnson, SQLite internals: WAL (https://fly.io/blog/sqlite-internals-wal/), core. 15 min. The write-ahead log, frame by frame. Makes rung L4's stretch step legible.

Alongside: Open a second terminal and `watch ls -la t.db*` while you insert rows in WAL mode; watch `-wal` grow and the main file stand still.

Guess questions (ask before the reading or the prediction):
- Where does a write go first in WAL mode? When does the main database file change?

### Step 2 · read · Reading 3: SQLite, Write-ahead logging, the first half

Read SQLite, Write-ahead logging, the first half (https://sqlite.org/wal.html), core. 20 min. Why the WAL exists, what a WAL "checkpoint" means there (folding the log back into the main file; a different meaning from a Sprite checkpoint).

Alongside: `pragma wal_checkpoint;` and look at the `-wal` size before and after.

Guess questions (ask before the reading or the prediction):
- What does the word checkpoint mean on this page? What is the cost of never running one?

### Step 3 · read · Reading 4: Designing Data-Intensive Applications (DDIA), chapter 3, first half: hash indexes, SSTables, LSM-trees

Read Designing Data-Intensive Applications (DDIA), chapter 3, first half: hash indexes, SSTables, LSM-trees (https://dataintensive.net/), core. 60 min. Append-only logs and compaction (merging old log segments), the same idea at database scale. An SSTable is a sorted log segment; an LSM-tree is a stack of them. You own the book.

Alongside: Type the chapter's `db_set` / `db_get` into bash, insert 100,000 keys, time one `db_get`. That number is why the rest of the chapter exists.

Guess questions (ask before the reading or the prediction):
- The chapter opens with the simplest possible database, two shell functions. Before reading: write them yourself, and say what is slow about them.
- What is an index, in one sentence, and what does it cost on writes?

### Step 4 · read · Reading 5: Ben Johnson, Litestream: how it works

Read Ben Johnson, Litestream: how it works (https://litestream.io/how-it-works/), optional. 10 min now, again at L4. Read it once so the word WAL has a picture attached.

Guess questions (ask before the reading or the prediction):
- How can a separate program replicate a SQLite database without SQLite cooperating?

### Step 5 · do · Mission step 1

Write `kv.py`, about 60 lines, with two modes. `set(key, value)` appends one JSON line to `kv.log`. `--write`: a loop that sets keys 1, 2, 3 ... with a few kilobytes of value each and prints each key the moment `set` returns (that print is the acknowledgement). `--verify`: replay the log line by line, print how many records were read, how many were torn (a line that fails to parse) and dropped, and the last good key.

### Step 6 · do · Mission step 2

Trial A, buffered. In `set`, call `f.write(line)` and nothing else. Terminal 1: `python kv.py --write`. Terminal 2, a few seconds later: `pkill -9 -f 'kv.py --write'`. Then `python kv.py --verify`. Compare the last key terminal 1 printed with the last good key `--verify` found. Expect a gap of hundreds of keys, and possibly a torn last line: Python's file object buffers in your process, and the kill destroys that buffer.

### Step 7 · do · Mission step 3

Trial B, flushed. Add `f.flush()` after the write (the bytes now belong to the kernel's page cache, which outlives your process). Repeat the kill three times. Expect no gap: the kernel keeps what your process handed it.

### Step 8 · do · Mission step 4

Trial C, the one you cannot run. Add `os.fsync(f.fileno())` after the flush. Nothing changes under `kill -9`, and that is the lesson: fsync protects against a crash of the machine, not of the process, and this mission cannot pull the plug. Measure instead what it costs: time 1,000 sets with and without fsync.
