Then open OSTEP, "File System Implementation". Read from the start through the section titled "Overall Organization", and stop when the next section (about the inode) begins. That's about two pages.

Before you read, write a guess in the L0 page's first "Read actively" box: how does the filesystem get from the name notes.txt to the disk blocks holding its bytes? As you read, look hard at the picture of the 64-block disk. You'll use its numbers in step 4.

12 min

The chapter says the disk is split into 4 KB blocks. Is your Mac's disk like that? Ask it:

diskutil info / | grep "Block Size"

Now open step2_blocks.py and write the two functions marked TODO: blocks_needed (how many 4 KB blocks a file of some size needs) and allocated_bytes (how much disk the filesystem says a file takes, from os.stat). The docstring for allocated_bytes has a warning about units. Read it. Then try your code on the files in this folder, and run the check:

python3 step2_blocks.py
python3 check.py step2

What you should see: step2: PASS and a small table. A 1-byte file takes 4096 bytes on disk, and a 4097-byte file takes 8192. If the check says you are off by a factor of 8, that is the units warning.

10 min

This is the L0 page's mission, steps 1 and 2. A container image is a stack of archives that has to be downloaded and unpacked before anything can run. Starting a container from an image you already have is a different cost. How different?

Guess before you measure. Open step5_timing.py and fill in the two predictions in seconds: the pull of python:3.12 from nothing, and one docker run once it's local. Then start the measurement (it removes any local copy first, so the pull is from nothing):

python3 run_timing.py

What you should see: Docker's download progress, one layer per line, then pull: ... s and three run times. The image is around 1 GB, so the pull can take a few minutes. Don't wait for it. Go to step 6 now and come back when it prints "Saved timings.json".

When it's done, write median() in the same file and run:

python3 check.py step5

What you should see: a predicted-versus-measured table and PASS if your ratio was within 3x. If it wasn't, the check asks for one sentence in SURPRISE on what you had wrong. That sentence is the most useful thing you'll write tonight.

12 min

While the pull runs, read Julia Evans, "What even is a container: namespaces and cgroups". It's short and it's the whole idea of tonight's last step.

Before you read, guess in the L0 page's second "Read actively" box: three containers are running on one machine. How many kernels are running? As you read, note the word namespace each time it comes up, and what it hides.

15 min

On a Mac there's a twist. The machine a container runs on is not macOS. Docker Desktop runs a hidden Linux virtual machine, and every container is a process inside it. So "outside" means that VM, and run_compare.py reaches it with the nsenter command from the L0 page.

Open step7_inside_outside.py. For each of five commands, predict whether the container prints the "same" output as the Linux VM or "different" output. Then one True or False: when a container runs sleep 300, can the VM's process list see it? Fill everything in, then:

python3 run_compare.py
python3 check.py step7

What you should see: a table of the five commands in three places (your Mac, the VM, the container), then the check marks each wrong prediction. For each one, write a sentence in NOTES and run the check again until it says PASS. Look at the kernel version line in particular, and compare it with what Julia Evans said about kernels.

Want to see it by hand? docker run --rm -it python:3.12 sh gives you a shell inside a container. Type hostname, then exit. This part is optional.
