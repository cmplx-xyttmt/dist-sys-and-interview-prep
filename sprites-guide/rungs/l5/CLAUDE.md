## After this rung he can say

- what copy-on-write means: readers share one copy; a writer gets a private copy of only the part it changes
- how an overlay filesystem works: a read-only lower directory, a writable upper directory holding only the changes, a work directory the kernel uses internally, and a merged view that shows both
- why a virtual-machine snapshot can be taken in milliseconds (memory and disk are marked copy-on-write rather than copied) and what Firecracker's snapshot and restore do
- why forking a disk from a snapshot is cheap, and why Sprites cannot yet do it natively: restore is in-place, and fork-from-checkpoint is a requested feature as of mid-2026. The explainer's section 05 describes forking as if it shipped; treat that paragraph as the plan, not the product

## The steps

### Step 0 · read · Reading 1: Julia Evans, How containers work: overlayfs

Read Julia Evans, How containers work: overlayfs (https://jvns.ca/blog/2019/11/18/how-containers-work--overlayfs/), core. 10 min. Lower, upper, merged, with the exact mount command the mission uses.

Alongside: In the mission's container: `rm merged1/b.txt; ls -la upper1`. The odd entry you see is a whiteout, a marker that hides the lower file.

Guess questions (ask before the reading or the prediction):
- Where do writes through the merged view go? What happens when you delete a lower-layer file through merged?

### Step 1 · read · Reading 2: Linux kernel documentation, Overlay filesystem, the first two sections

Read Linux kernel documentation, Overlay filesystem, the first two sections (https://docs.kernel.org/filesystems/overlayfs.html), optional. 15 min, if you want the rules for whiteouts and directory merging.

Guess questions (ask before the reading or the prediction):

### Step 2 · read · Reading 3: Firecracker, Snapshot support documentation

Guess questions (ask before the reading or the prediction):

Read Fly.io, The design and implementation of Sprites, the section headed "Decision #2: Object Storage For Disks" (https://fly.io/blog/design-and-implementation/), core. 20 min. Where checkpoints and the block device live in the real design. The other sections are rung L8.

Read Fly community, Feature request: native fork Sprite from checkpoint (https://community.fly.io/t/feature-request-native-fork-sprite-from-checkpoint/28191), core. 5 min. The honest state of forking, needed for the last condition below.

Guess questions (ask before the reading or the prediction):
- Why is fork harder than restore in Fly's design?

### Step 5 · do · Mission step 1

Overlay mounts are a Linux kernel feature, so do this inside Linux: `docker run --rm -it --privileged ubuntu bash` gives a root shell in a container that is allowed to mount. One trap: the container's own root filesystem is itself an overlay, and the kernel refuses an upper directory that sits on an overlay. So first `mkdir /ov && mount -t tmpfs tmpfs /ov && cd /ov` and work there.

### Step 6 · do · Mission step 2

Make `lower/` with three small files `a.txt b.txt c.txt`, copy it to `lower.orig/`, and make empty `upper1 work1 merged1` (and the same with 2 and 3). Mount: `mount -t overlay overlay -o lowerdir=lower,upperdir=upper1,workdir=work1 merged1`, and likewise for 2 and 3.

### Step 7 · do · Mission step 3

`echo changed > merged1/a.txt`, `echo changed > merged2/b.txt`, `echo changed > merged3/c.txt`. Then `diff -r lower lower.orig` (must print nothing) and `ls upper1 upper2 upper3` (one file each).

### Step 8 · do · Mission step 4

Back on the Mac, in `chunks.py`: add `fork(label, new_name)`, which copies a checkpoint's manifest under a new name, and `shared(a, b)`, which prints how many hashes two manifests have in common out of the total. Fork `big.bin`'s checkpoint as `big-fork`, change the middle of the forked file and put it again under that name, then run `shared`.
