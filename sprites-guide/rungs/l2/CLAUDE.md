## After this rung he can say

- what a cryptographic hash (such as SHA-256) gives you here: a fixed-size name that is a function of the content, so two identical blobs get one name and a changed blob gets a new one
- what content addressing means: store each blob under its hash. A blob under a given name can never change, so a copy of it can never be out of date
- how git stores a repository as a graph of immutable objects (blobs, trees, commits) and why a commit is cheap: it is a few pointers over objects that already exist
- why deduplication falls out for free, and why a snapshot of content-addressed data is a small manifest (a list of names) rather than a copy of the data
- what JuiceFS is, since the explainer's storage section is built on its model: a filesystem that stores file data as chunks in object storage and the metadata (which chunks make up which file) in a separate database. The same split as Google's 2003 GFS paper, which had one metadata server and many chunk servers

## The steps

### Step 0 · read · Reading 1: Pro Git, 10.2 Git internals: Git objects

Read Pro Git, 10.2 Git internals: Git objects (https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), core. 30 min, with a terminal open. Do the `hash-object` and `cat-file` examples; the aha is watching a tree object point at blob hashes.

Alongside: `git init t && cd t && echo hi > a && git add a && git commit -qm x && find .git/objects -type f | wc -l`; change `a`, commit again, count again.

Guess questions (ask before the reading or the prediction):
- What is a commit made of? If you change one file in a repository of 1,000 files and commit, how many new objects are created?

### Step 1 · read · Reading 2: Pro Git, 10.3 Git references

Read Pro Git, 10.3 Git references (https://git-scm.com/book/en/v2/Git-Internals-Git-References), optional. 10 min. A branch is a 41-byte file holding a hash. That is what a checkpoint pointer is.

Alongside: `cat .git/refs/heads/main` and `wc -c` on it.

Guess questions (ask before the reading or the prediction):
- What is in the file `.git/refs/heads/main`? How big is it?

### Step 2 · read · Reading 3: JuiceFS, Architecture

Read JuiceFS, Architecture (https://juicefs.com/docs/community/architecture/), core. 10 min. The data / metadata split in one diagram. This is the page the explainer's section 07 means by "the JuiceFS design doc".

Alongside: Draw the architecture from memory first, then compare with the page's diagram.

Guess questions (ask before the reading or the prediction):
- Where do file names live and where do file bytes live? What happens to your files if the metadata engine dies?

### Step 3 · do · Mission step 1

Write `chunks.py`: `put(path)` splits the file into 64 KB chunks, computes `sha256` of each, writes each chunk to `store/<hash>` if not already there, and writes `manifests/<name>.json` holding the ordered list of hashes and the total length.

### Step 4 · do · Mission step 2

`get(name, out)` rebuilds the file from the manifest. Check with `cmp`.

### Step 5 · do · Mission step 3

Make a 10 MB test file (`head -c 10000000 /dev/urandom > big.bin`), put it, count the files in `store/`. Copy it, append one line, put the copy; count again. The difference is the number of new chunks.

### Step 6 · do · Mission step 4

Add `checkpoint(name, label)`, which copies the manifest to `checkpoints/<label>.json`, and `restore(label)`, which copies it back over `manifests/<name>.json`. Neither touches file data; `get` is what rebuilds a file. Print the byte size of the checkpoint file.

### Step 7 · do · Mission step 5

Afterwards, re-read the explainer's section 05 (explainer.html#checkpoint) "Predict first" box. It should now read as obvious.
